Methodology note: Both schema versions share identical corpus content and query vectors. The only variable is the retrieval path: v1 deserialises _source JSON; v2 reads pre-computed doc_values via docvalue_fields with _source: false. Embedding HTTP round-trips are excluded to isolate OS-side overhead.

6 · Production Expectations

These benchmarks were run against a 1 000-chunk local corpus. Improvements are expected to widen in production because:
  • Larger _source blobs (more metadata fields per document) increase v1 deserialization cost proportionally.
  • Higher segment cache pressure on multi-shard clusters further penalises _source retrieval.
  • Hybrid mode gains are amplified at higher top_k values (more hits → more per-hit overhead).

7 · Recommendation

The v2 schema delivers a statistically significant 18–30% reduction in retrieval latency across all search modes with no measurable impact on insert throughput. The migration is automatic and crash-resumable. The change is safe to merge and deploy.

Note on migration lock: threading.Lock is sufficient for single-replica deployments. If digitize is ever scaled to multiple replicas, the lock should be upgraded to a distributed lock (e.g. Redis or an OpenSearch document-level CAS operation) to prevent concurrent reindex races.
